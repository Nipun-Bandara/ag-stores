# Product pricing and packing — stage 1

Implemented on `refactor/product-pricing-and-packing`. This stage introduces product identifiers and whole-unit / kilogram selling. Category management and product UUIDs remain unchanged. A sealed 1 kg packet can be a UNIT product; KG means stock and price are measured by weight.

## Decisions

- `itemCode` and `barcode` are separate trimmed text fields (maximum 100 characters). Leading zeros are preserved. Each has its own shop-scoped unique index; an item code does not collide with a different product's barcode. Comparisons are case-sensitive. Barcode whitespace/empty values normalize to null. Multiple null identifiers are allowed. Uniqueness races return HTTP 409 with a clear duplicate-name/code/barcode message.
- New products and full product edits require an item code. Legacy products retain null codes until their full edit; stock and availability shortcuts do not force a code assignment. No synthetic POS codes are generated. Owner search covers both identifiers; a keyboard scanner can type into search and submit with Enter. Identifier fields accept text and suppress scanner Enter to prevent accidental product submission. There is no camera scanner or billing screen.
- `sellingUnit` is UNIT or KG. New UNIT products automatically use minimum 1 and increment 1. New KG products automatically use minimum 0.002 kg. Ordering increments do not apply to KG requests; the existing required increment column stores 0.001 as precision metadata. Customers type weights with at most three decimal places, at or above the saved minimum (never below 0.002 kg), and no greater than stock. KG quantities need not be multiples of an increment. Existing products retain their saved minimum. UNIT products use plus/minus controls; KG product cards/details use a weight field with an explicit add/update action, and cart weight fields apply on blur or Enter.
- Quantities use PostgreSQL `Decimal(13,3)` and an application limit of 2,147,483,647. Application quantity arithmetic uses integer thousandths (`BigInt`). JSON quantities are numbers within that safe scaled range; parsing rejects extra precision rather than silently rounding it. Prices and monetary totals remain exact two-decimal strings/decimals. Each line is rounded half up to cents, then rounded lines are summed. Example: LKR 10.01/kg × 0.5 kg = LKR 5.01; two separate LKR 0.01/kg × 0.5 kg lines sum to LKR 0.02.
- Product lists/details, owner stock shortcuts, cart and checkout, order details, dashboard/report inventory and report exports show units. Best-selling report rows group by the order item's snapshotted unit, so a product's historic UNIT sales are not added to its later KG sales. Basket badges count distinct product lines, not a sum of units and kg: 0.5 kg of one product is one item.
- New order items snapshot `sellingUnit`. Migration backfills old items with UNIT without changing prices or historical order totals. Historical line totals use the stored unit price and quantity, never the current product price.
- A selling-unit change requires both existing and submitted stock to be zero and no active orders. Delivered, cancelled, rejected and failed-delivery orders are terminal. The check runs with a product row lock inside the existing serializable transaction/retry mechanism. Ordinary price/minimum/increment edits remain allowed; stale cart selections are revalidated rather than coerced.
- Existing customer-specific v2 carts remain readable. Missing selling metadata means legacy UNIT, minimum 1, increment 1. Quantities are retained. Requests lacking a unit are likewise interpreted as legacy UNIT; they cannot silently become kg. A unit mismatch or newly invalid quantity produces a checkout error. The customer must review the selection, or explicitly remove and re-add the product to accept its new setup. Existing malformed storage filtering and customer isolation remain in place.
- Server validation, database prices and conditional stock decrements remain authoritative. Reservation, order write, notifications and rollback remain in one transaction. Cancellation/rejection restores the stored fractional amount exactly once through the existing state machine. Price/stock audit writes remain transactional. Raw-lock SQL serialization/deadlock errors are included in bounded transaction retries.

## Migration and local operation

1. Back up the intended development database and stop old application processes. Confirm `DATABASE_URL` targets the database you intend to migrate. Do not reset it.
2. Run `npm run db:generate`, then `npm run db:migrate:deploy`.
3. Run `npm run typecheck`, `npm run lint`, and `npm run build`; restart the app with `npm run dev` (or the production start command after building).
4. The migration `20261101100000_product_selling_setup` adds identifiers/setup/unit snapshots, converts stock/threshold/order quantities from integers to decimals, and adds shop uniqueness and quantity checks. Existing prices, UUIDs, category links, stock amounts, and order money are preserved. Existing products become UNIT / minimum 1 / increment 1. No seed or backfill of item codes is required.
5. Integration tests require an isolated migrated database. Set **both** `DATABASE_URL` and `TEST_DATABASE_URL` to that database. Existing integration suites also require the standard development seed. Never point these fixture-writing tests at production. For a multi-suite run use `--maxWorkers=1`, and set `AUTH_RATE_LIMIT_MAX_ATTEMPTS=1000 AUTH_RATE_LIMIT_MAX_ATTEMPTS_PER_IP=10000` to avoid test logins sharing rate-limit buckets.

## Exact manual acceptance steps

Use an open shop with minimum order amount 0, a saved customer address within its delivery radius, and note its delivery fee F. Use a fresh item code/barcode if these examples already exist.

1. Owner → Products → Add product. Select the existing shop/category. Enter name `Stage 1 Rice`, item code `000123`, barcode `000000456`, selling type KG (minimum automatically 0.002 kg, increment not applicable), price/kg `10.01`, stock `2.5`, threshold `0.5`; save. Expected: values and leading zeros remain, stock is 2.5 kg, and the four form groups are visible. Search for each full identifier (or focus search, scan, Enter). Expected: this product appears. Scan into an identifier field while editing; Enter must not save the form.
2. Create another product in the same shop with item code `000123` and a different name/barcode. Expected: duplicate conflict and no new product. Repeat with a new item code but barcode `000000456`. Expected: same clear conflict. Create products with distinct codes and blank barcodes. Expected: both save. Another owned shop may reuse either identifier; another owner's products must not appear or be editable.
3. Create `Sealed Rice 1kg` as UNIT, minimum/increment 1, stock 3. Expected: UNIT stays selected despite the name. Try stock `1.5` in the UNIT form and quick stock editor. Expected: rejected. Edit an existing legacy product: expected blank code, unchanged price/stock/category, and code required on full save.
4. Customer → Rice detail: type `0.5` kg and use Add. Expected: 0.5 kg and subtotal LKR 5.01. Update to `0.501` kg: valid without increment restrictions. In cart, type a new weight and blur or press Enter to apply it. Reject `0.001`, a fourth decimal, or a quantity exceeding stock. Accept `0.002` and `0.003` when stock permits. Set back to `0.5` kg for checkout. The basket badge counts one product line.
5. Checkout and place order. Expected: authoritative subtotal 5.01, total 5.01 + F, order line `0.5 kg`, stock now exactly 2 kg. Cancel while PLACED. Expected: stock 2.5 kg and the cancelled order still says 0.5 kg. A repeated cancellation must fail without restoring again. Repeat an order for 0.375 kg and reject it as owner. Expected: stock returns exactly to 2.5 kg.
6. Open checkout for 0.5 kg, then close the shop in another owner session before placing. Expected: placement fails, no order is created, and stock stays unchanged. Reopen the shop. With stock 0.5 kg, place 0.5 kg orders concurrently in two customer sessions. Expected: exactly one succeeds; stock is 0, never negative.
7. Try changing KG to UNIT while stock is nonzero: rejected. Set stock 0 with a PLACED order outstanding and try again: rejected. Cancel/reject active orders, set stock 0, then change type with whole minimum/increment/threshold values: succeeds. Expected: previous order lines retain kg. A saved KG cart cannot silently become UNIT and is blocked at checkout until reviewed/removed/re-added.
8. Edit a KG product minimum to 0.3 with stock 0.35. Expected: available, with a minimum supported weight of 0.3 (no increment rounding). Stock below the minimum is out of stock. Confirm fractional low-stock filtering and labels.
9. Switch to Sinhala and repeat form editing, cart, checkout errors, product details and order views. Expected: translated interface labels and explicit kg/units. In reports/export, units accompany quantities and historic UNIT/KG sales remain separate.
10. Before migrating, save a normal customer cart; after migrating, sign back into the same customer. Expected: quantities unchanged and UNIT interpretation retained. If a product was changed to KG, checkout blocks the stale selection and requests review.

## Remaining stages and limitations

Stage 1 contains no tier discounts, wholesale pricing, packed-weight fields/editing, packaging conversion, POS billing or camera scanning. Those need separately approved stages; their precise scope and migration design remain to be specified. Free-text names/descriptions are not interpreted as pack weight. A physical scanner/device and the full bilingual browser workflow still require manual acceptance. Unit conversion does not convert existing stock: clear/resolve stock explicitly before changing a unit.
