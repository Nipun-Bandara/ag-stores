# Product photos

Product photos use the existing application sessions, PostgreSQL database, and product routes. Supabase is used only for public image objects. The owner can keep one managed photo per product; historical external `imageUrl` values continue to render without a conversion or network fetch.

## Setup and migration

1. Create a Supabase **Free** project. In Storage create a public bucket named exactly `product-photos`. Set allowed MIME types to `image/webp` and bucket maximum file size to **2 MB**. Do not create public `INSERT`, `UPDATE`, or `DELETE` policies for this bucket. Public bucket reads do not grant writes; the application server uses a secret key for writes after checking its own session and shop ownership. See [Supabase buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) and [access control](https://supabase.com/docs/guides/storage/security/access-control).
2. Copy the project's **secret** API key (`sb_secret_...`) into `SUPABASE_SECRET_KEY` in the server environment. The project URL may be set as `SUPABASE_URL` or reused from `NEXT_PUBLIC_SUPABASE_URL`; if both are set, they must point to the same project. `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` is not used for photo writes. Older projects can use a legacy `SUPABASE_SERVICE_ROLE_KEY` instead. Never prefix a secret or service-role key with `NEXT_PUBLIC_`, send it to a browser, or add it to source control. Restart the development server after changing `.env`. No Supabase Auth or Supabase database connection is needed. See [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).
3. Apply the normal database migration after backing up the existing database: `npm run db:generate` then `npm run db:migrate:deploy`. The migration adds a nullable managed-object key and an upload ledger; it does not rewrite old image URLs or product records. On an existing database, first ensure its applied migration history matches this checkout.
4. Deploy the application with the project URL and server-only secret key. A missing/invalid storage configuration causes an actionable upload error; product browsing and legacy images continue to work.

The route must run in a Node.js server with Sharp available. Its request ingress must allow at least **10 MB plus 64 KB multipart overhead**; a hosting platform with a lower hard request-body limit will reject large files before the application can process them, so lower the documented original-size limit for that platform. The app reads at most this bound, accepts JPEG/PNG/WebP, decodes up to **40 million pixels**, applies EXIF orientation, scales to **1600 × 1600** maximum, re-encodes WebP without original metadata, and rejects outputs over **2 MB**. HEIC/HEIF must be exported as JPEG first. Objects have random keys under `products/{shop UUID}/`, not user filenames. No paid Supabase image transformations are used.

## Save and cleanup

The form uses the shared Attachment component for the local preview, filename, file size, upload state, and remove action. Choose photo opens the device file picker. Take photo opens an in-page camera preview when getUserMedia is available; camera access requires permission and a secure context (HTTPS or localhost). Otherwise, the native device camera/file picker is used. Camera streams are stopped when the dialog closes. The form keeps a local preview until Save. The authenticated upload endpoint validates/optimizes the file and creates an upload ledger record for the exact owner, shop and optional product. A product save accepts only a matching, unused ledger ID; a client URL or storage path cannot claim a managed object. A failed save leaves the prior photo and the new upload available for retry. Replacement/removal updates the product reference first, then attempts deletion of the previous managed object. External legacy URLs are never deleted. If deletion fails, the product save remains successful and cleanup retries later.

Run `ALLOW_PRODUCT_PHOTO_CLEANUP=1 npm run db:photos:cleanup` from the deployed server environment on a schedule, for example daily. It scans uploads older than **24 hours**, checks live product references, and handles up to 100 unreferenced objects per run. It marks them so they cannot later attach, retries failed Storage deletions on the next run, and records completed deletions so they are not retried forever. Run more often if the shop has over 100 abandoned uploads per day. Keep an alert on a nonzero exit code. A lost response after a successful upload may leave an unreferenced object for this grace period; referenced photos are never removed by this job. The application database and Storage are separate systems, so the ledger is the recovery path for a failed cleanup.

Supabase's current Free allowance is [1 GB stored objects](https://supabase.com/docs/guides/platform/manage-your-usage/storage-size) and [10 GB transfer (5 GB cached + 5 GB uncached)](https://supabase.com/docs/guides/storage/serving/bandwidth). The Free project's global per-file ceiling is [50 MB](https://supabase.com/docs/guides/storage/uploads/file-limits); this app and bucket deliberately use smaller limits. Check the project's Usage page for storage size and egress as catalogue traffic grows. These service quotas can change; confirm them in the dashboard before launch.

## Manual checks

1. As an owner, create a product with **Choose photo** and a JPEG/PNG/WebP from the gallery. Expect a preview immediately, then a saved thumbnail in the owner list and a photo on customer cards/details. The image should remain after reload.
2. On a phone, create another product using **Take photo**. Expect the rear camera where supported and correct orientation after save. On desktop, expect a live camera preview after permission is granted. Capture a photo and confirm it appears in the attachment. Deny permission and check the error and native device-camera fallback.
3. Enter other product fields, open the camera/file picker, then cancel. Expect all entered fields and the prior image/selection to remain unchanged.
4. Edit a product and replace its photo. Expect the previous image until Save succeeds, then the new image in owner and customer views. Remove it and save; expect the fallback after reload.
5. Open an existing product with an external `imageUrl`. Expect it to display without reuploading. Edit other details and save; expect the legacy URL to remain. Remove it only by using the photo remove control.
6. Select an SVG, HEIC, or file over 10 MB. Expect an inline actionable error and no upload. Rename a non-image as `.jpg` and submit; expect server rejection. Try a large-dimension image; expect a dimension error.
7. Interrupt the upload network request, then retry Save. Expect the selected preview and other fields to remain, no product saved without the photo, and a successful retry when the network returns. Force the product save to fail after upload (for example a duplicate item code); expect the previous image intact and a later retry with corrected data to reuse the uploaded photo.
8. As an owner of another shop, attempt the upload endpoint and product update with the first shop's IDs/upload ID. Expect 404/409 and no reference or deletion change.
9. Review English and Sinhala labels, errors, toasts, and the responsive form/list on mobile and desktop. Confirm missing/broken images show a fallback.

Live Storage upload and deletion require project credentials and a configured bucket. Tests use mocked Storage requests; do not interpret a green test run as a live Supabase upload.
